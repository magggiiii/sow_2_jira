01 — The big picture

Four things explain almost everything we found.

Strip away the detail and the 83 findings collapse into four root themes. Fix these four and the system stops being a demo and starts being a product.

01

There's no concept of "who"

The app has no users, accounts, or logins anywhere in it. Everything lives in one shared pile on the machine's hard drive. The moment two people use it, they'd see each other's documents — and unknowingly spend each other's AI and Jira credentials.

Blocks multi-user
02

The work happens in a fragile place

A long extraction job runs inside the website process and saves everything to local disk. On a hosted platform that disk gets wiped on every routine update — so a job in progress is lost, finished results vanish, and the AI bill has to be paid all over again.

Data loss on deploy
03

The smart core is mis-firing

On the first real document, the AI pipeline flagged 100% of tickets as “incomplete,” merged zero duplicates, and the quality-checker had zero confidence in its own answers. Most of this traces to a single overly-tight setting that quietly cuts long AI responses off mid-sentence.

Output not yet trustworthy
04

The doors are unlocked

No login means anyone with the link could run up bills or read everything. Secret keys can get baked into the shipped app. And the headline “Push to Jira” button is actually broken right now — it crashes every single time it's pressed.

Security & a dead feature

03 — What needs fixing first

The issues that genuinely block launch.

In plain terms — the problem, and the fix. Each one is tied to real lines of code in the audit.

Critical

The “Push to Jira” button is broken

The product's headline feature crashes the instant it's used — a missing line of code means every push fails. It clearly hasn't been run since a past refactor.

The fix

One-line import fix, plus an automatic test so this can never silently break again.

server.py:664 · NameError on every push
Critical

Secret keys can leak into the shipped app

There's no rule telling the build what to leave out, so a real GitHub token and other live secrets get copied into the packaged application — recoverable by anyone who can inspect it.

The fix

Add a 6-line ignore file and rotate the exposed keys. ~10 minutes. This is the single best effort-to-payoff fix in the whole report.

no .dockerignore · Dockerfile COPY . .
Critical

Anyone with the link gets in

There is no login on any screen or action. On the open internet, a stranger could upload files, trigger AI spend, and read or delete every document.

The fix

Add Google sign-in (limited to your company), and tie every piece of data to the person who owns it.

every /api route · no auth guard
Critical

Users would spend each other's credentials

Everyone's AI and Jira keys are stored in one shared slot. If two people run jobs at once, one person's work quietly gets billed to — and pushed under — the other person's account.

The fix

Give every user their own encrypted keys in the database, used only for their own runs.

shared settings + os.environ credentials
Critical

Long jobs die on every update — and lose everything

Extraction runs inside the web server and keeps all its progress in memory. A routine restart kills the job halfway with no way to resume, so the whole document has to be re-processed (and re-paid for).

The fix

Move heavy jobs to a dedicated background worker with a proper queue, so they survive restarts and scale up.

in-process BackgroundTask · no checkpoints
Critical

Saved work disappears on every deploy

All documents, results, and history are written to the local hard drive — which a hosted platform erases on each update. Your session list would silently empty out after every release.

The fix

Move data to a real database and file storage that persist independently of the app.

data/sessions, SQLite, settings.json on disk
Critical

The “100% incomplete” flag bomb

A coverage checker marks every ticket “incomplete” the moment it suspects anything is missing — even when the answer is low-confidence or already covered elsewhere. The useful signal gets buried in noise.

The fix

Only flag when the checker is actually confident, run the check after de-duplication, and treat it as advice — not a verdict on every ticket.

orchestrator ignores the confidence score
Critical

One tight setting breaks the AI's output

A hard cap on AI response length cuts long answers off mid-list. The code then quietly fails and pretends it succeeded — which is why de-duplication merged nothing and ~29 of 30 extraction failures share the same signature.

The fix

Ask the AI for guaranteed-valid structured output, size the limit to the request, and process duplicates in smaller batches. This one change fixes most of the quality problems at once.

llm_client.py:501 · max_tokens=4096
High

Failures are invisible — they look like success

When a step errors out, the system silently returns an empty result and carries on as if all is well. That's why three serious bugs shipped unnoticed until a human counted 509 tickets by hand.

The fix

Add a per-run quality report and mark a run “degraded” when something's clearly off.

broad except → silent no-op in every agent
High

Pushing many tickets can create duplicates

If a large Jira push fails partway (a rate limit or a restart), pressing push again re-creates the tickets it already made — leaving a messy, half-duplicated project.

The fix

Remember which tickets already exist and skip them on retry, with proper rate-limit handling.

no idempotency on create_issue

04 — The plan

From prototype to product, in waves.

The work is sequenced so each wave unlocks the next. Start with the things that are cheap and urgent; finish with polish.

⚡

Do this today — the 10-minute win

Add the ignore-file so secrets stop leaking into builds, and rotate the exposed tokens. Almost no effort, closes a live security hole immediately. There's no reason to wait on this one.

0Hardening

Make the repo safe to ship from

Fix the broken Jira button, lock down secrets, pin dependencies, and set up automatic testing so nothing regresses from here on. No user-facing change — it just makes everything after it provable.

Unblocks launchEffort: Medium
1Foundation

Real database & per-user secrets

Stand up the database and file storage that everything multi-user depends on, and give each user their own encrypted keys. The pipeline still runs as before — we're only changing where things are stored.

Unblocks launchEffort: Large
2Multi-user

Logins, isolation & a durable worker

Add sign-in, keep each user's data fully separate, and move long jobs onto a background worker that survives restarts and scales. This is the biggest change — and the heart of becoming a real product.

Unblocks launchEffort: Extra Large
3Quality

Fix the smart core

Repair the extraction, de-duplication and quality-checking bugs so the output is actually trustworthy. Best landed before going live, so the product ships a working engine — not the current noise.

Effort: Large
4Go live

Deploy to the cloud & monitor it

Ship the whole thing to Render as proper connected services, and replace the over-built monitoring with clean, hosted logging and AI-call tracing.

Unblocks launchEffort: Large
5Polish

Clean up & harden

Make Jira pushes duplicate-proof, delete the old laptop-only code, and tidy the interface. Quality-of-life — done after launch.

Effort: Medium
